## Before you update

- **The first launch after updating reads all your Claude logs again, once.** [#537](https://github.com/Nanako0129/syrtis/pull/537)

  The Claude parser changed (see Fixes). On the maintainer's data, 5,323 files and 11 GB, the first refresh took about a minute of high CPU, measured on 2026-11-03 on a busy Mac: 34 s of CPU at a machine load of about 6, and 58 s at about 14. More history can take longer. While it runs, the menu bar title and the popover's background reports can wait behind it. Droid, Qwen, Roo Code, Kilo Code and Cline are also read again once; how long that takes was not measured.

- **Going back to v2.10.0 or earlier after this update loses some Claude history unless you restore a backup.** [#537](https://github.com/Nanako0129/syrtis/pull/537)

  Older versions can't read the new Claude cache. They rebuild it from your Claude logs and drop every turn that only the cache still holds, because Claude Code has since removed it from its own logs by compacting. The same happens if an older build scans the same folder after v2.11.0 has written to it, so don't run the two side by side.

  To keep the option open, quit Syrtis and any tokscale process before you install the update, then copy `cache/source-message-cache-v2/claude/` from `~/.config/tokscale` (or from the folder `TOKSCALE_CONFIG_DIR` names, if you set it). To go back:

  1. Quit everything that runs v2.11.0.
  2. Put the copied `claude/` folder back in the same place.
  3. Start the older version.

  Don't start any other version before the restore is finished. Without a copy, the loss stands.

## Features

- **Settings has an Accounts page.** [#533](https://github.com/Nanako0129/syrtis/pull/533)

  Claude, Antigravity and Cursor moved there from General, next to two new sections for Pi and DeepSeek Harness. Each section has a one-line summary and an info button for the longer explanation. Turning on Cursor sync no longer shows its privacy paragraph inline: it opens a confirmation with Cancel and Continue, and nothing is enabled until you press Continue.

- **Pi can read additional folders.** [#525](https://github.com/Nanako0129/syrtis/pull/525) — thanks [@savourylie](https://github.com/savourylie)

  "Add folder…" in the Pi section of Settings → Accounts adds a folder of Pi session-format JSONL files, such as a usage-only export from a headless `--no-session` run, which writes nothing under `~/.pi/agent/sessions`. The folders merge into the Pi total with no per-folder breakdown, and a response found in two files counts once. Your home folder, a folder that contains it and `/` are refused.

- **DeepSeek Harness can read the sessions folder of another DSH home.** [#534](https://github.com/Nanako0129/syrtis/pull/534) — thanks [@darkskygit](https://github.com/darkskygit)

  Add `<DSH_HOME>/sessions` under DeepSeek Harness in Settings → Accounts. Its usage joins your DSH total, and a session found in two folders counts once. The same folders are refused as for Pi.

- **Several Cursor profiles can sync into one Cursor total.** [#532](https://github.com/Nanako0129/syrtis/pull/532), [#535](https://github.com/Nanako0129/syrtis/pull/535) — thanks [@ohari5336](https://github.com/ohari5336)

  The Cursor section of Settings → Accounts lists "Cursor app (default)" and each folder you add with "Add Cursor profile folder…", a folder you start Cursor with using `--user-data-dir`. Up to 32 profiles can be added, and each row shows its own last result. An account signed in to several profiles is downloaded once, and the later rows say "Same account as another profile; counted once." Removing a profile deletes its downloaded usage the next time Syrtis can.

- **Antigravity conversation databases in `~/.gemini/antigravity/conversations` are read.** [#526](https://github.com/Nanako0129/syrtis/pull/526) — thanks [@rsimenok](https://github.com/rsimenok)

  The Antigravity desktop app writes there: on one Mac with Antigravity.app 2.26.0, Syrtis now shows about 28.8K tokens for it. The usage appears as "Antigravity Extension" inside the Antigravity tab, under the Antigravity subscription's quota, with no card of its own. A response that more than one Antigravity source reports counts once.

- **A custom OpenCode database location is scanned.** [#530](https://github.com/Nanako0129/syrtis/pull/530) — thanks [@sunjeel25](https://github.com/sunjeel25), whose Windows report this was ported from

  Syrtis read only OpenCode's default database. It now also reads `OPENCODE_DB` and `scanner.opencodeDbPaths` in tokscale's `settings.json` (in `~/.config/tokscale` or the folder `TOKSCALE_CONFIG_DIR` names). An edited `settings.json` is picked up by a later refresh, but `OPENCODE_DB` is read when Syrtis starts, so a changed value needs a restart. An `opencodeDbPaths` entry must be an absolute path, `~` is expanded, and a file whose name is not `opencode.db` or `opencode-<channel>.db` is skipped without a message. On a copy of the maintainer's 351 MB database moved elsewhere and named by `OPENCODE_DB`, Syrtis found the same 12,484 messages and 1,290,378,670 tokens as with the database in its default place.

## Fixes

- **Claude input tokens were overcounted for some requests.** [#537](https://github.com/Nanako0129/syrtis/pull/537)

  Some requests were counted at their full prompt size instead of the real cache split their transcript also reported. On the maintainer's data Claude input went from 47.96M to 19.63M (−59.1%), all for one model, `gemini-4-argon`; cost moved −0.23%, and output, cache and message counts did not change. A one-hour cache-write split that arrives before its total is no longer lost, and usage from Claude's advisor iterations is counted as its own rows, without adding to the message count.

- **A transcript symlinked into an extra Claude account's folder was counted for the main account too.** [#537](https://github.com/Nanako0129/syrtis/pull/537)

  A file under `~/.claude/projects` that is a symlink into an extra account's folder now counts for the extra account only. In the test fixture the main account went from 8,000 to 1,000 output tokens.

- **Opening the popover after the app had been idle was slow.** [#537](https://github.com/Nanako0129/syrtis/pull/537)

  A Claude transcript that only grew is now read from where the last scan stopped (Apple silicon Macs only), and on the engine's test session an append to a parent session rewrote 1 cache file instead of 119. On copies of the maintainer's data, the first open after two idle minutes took 3.7 s to show the graph, against 14.5 s on v2.10.0's engine, and the app's mean CPU went from 13.4% to 0.8%. The second run had a lighter machine load, so read the ratios as indicative.

- **Background refreshes use one core, and price lookups cost less CPU.** [#543](https://github.com/Nanako0129/syrtis/pull/543), [#542](https://github.com/Nanako0129/syrtis/pull/542)

  The menu bar title's usage and the popover's once-a-minute reports now run on one core instead of two; opening the popover and a manual refresh still use two. A popover load that arrives during a background scan of the same year waits for that scan. In a 10-minute run on the maintainer's data with the popover closed, total CPU went from 71.0 s to 58.9 s and the 10-second windows above 100% from 4 to 1; the one left is the first launch after the cache change above. After startup the two builds were within noise.

  Price lookups do less work, with identical reports. Measured in the engine on a heavily loaded machine, one graph computation took a median of 7.68 s of CPU instead of 10.42 s, and one model computation 7.01 s instead of 8.50 s.

- **Codex usage dropped out of reports once its sessions were compressed.** [#529](https://github.com/Nanako0129/syrtis/pull/529) — thanks [@patrick-fu](https://github.com/patrick-fu)

  Codex 0.166 compresses a rollout at least 7 days old into `.jsonl.zst` and deletes the plain file, and Syrtis read only plain files. The reporter measured about 5.06B of 12.59B Codex tokens missing over 15 days on one Mac. Syrtis now decodes those archives. Re-encoding 2,426 local rollouts the way Codex does gave the same totals as the plain files.

- **Roo Code, Kilo Code and Cline usage is read from VS Code on macOS and counted as upstream now counts it.** [#539](https://github.com/Nanako0129/syrtis/pull/539)

  Roo Code and Kilo Code tasks in VS Code's own `Code` folder (not Insiders, Cursor or VSCodium) are now scanned, so usage from a local VS Code install shows up for the first time. Three counting rules changed for all three:

  - A positive cost reported by the extension is kept as the extension's own and no longer re-estimated, so cost totals shift. An explicit 0 is still estimated.
  - For Roo Code and Kilo Code rows dated 2025-11-02 UTC or later, input no longer includes the cache buckets a second time, so input totals drop. Earlier rows change only on the OpenAI protocol. Cline's input is never reduced.
  - Some rows change provider, for example Kilo gateway rows from `openai` to the real vendor, and `kilo-auto/` is billed as `kilo`.

  Usage attribution matches on client, provider and model, so a saved assignment for a row whose provider changed no longer matches: check Settings → Usage attribution for Kilo Code, Roo Code and Cline.

- **Hermes, Qwen, Droid and Kilo CLI counts changed.** [#539](https://github.com/Nanako0129/syrtis/pull/539)

  - Hermes counted reasoning tokens twice. Output now excludes them, so Hermes token totals drop by the reasoning count on every row that reports it. Cost drops only on rows priced from tokens.
  - Qwen's cached prompt tokens leave the input count, and on OpenAI-compatible providers reasoning leaves the output count, so Qwen totals and estimated cost drop.
  - Droid replies are counted on the date each was written, not all on the day of the session's first reply. Tokens, cost and session counts are unchanged.
  - Kilo CLI skips the stub rows left by a migration (provider and model both `legacy`, a `ses_migrated_*` session, zero tokens and cost). A session's count drops only if it is made up entirely of such rows.

  There was no real Roo, Kilo, Cline, Hermes, Qwen or Droid data on the maintainer's machines, so these rules rest on the engine's tests.

- **Models priced from a reseller's listing are now priced from the vendor's own.** [#541](https://github.com/Nanako0129/syrtis/pull/541)

  When a row carries a provider, Syrtis now prefers that vendor's own price row over a longer-named reseller row such as Perplexity's `perplexity/anthropic/…` and `perplexity/openai/…`. Rows hinted `google` are priced from Google's own `gemini/<model>` entry instead of `perplexity/google/<model>` or OpenRouter's `google/<model>`. On the maintainer's data, with one frozen price snapshot and the same 77,556,402,589 tokens and 308,071 messages in every run, 4 of 76 model rows changed cost and the total went from $33,797.96 to $33,276.84 (−$521.12, −1.54%):

  | Provider | Change in cost | Where it came from |
  | --- | ---: | --- |
  | Anthropic | −$452.16 | All `claude-sonnet-5-5`: Perplexity's cache-read rate was 2× and it had no cache-write rate |
  | OpenAI | −$68.97 | −$6.04 is `gpt-5.3-codex` moving from Perplexity's 2× rate to OpenAI's; −$62.92 is `codex-auto-review` |
  | Google | $0 | |
  | xAI | $0 | |

  `codex-auto-review` has no price of its own. It is now estimated as `gpt-5.1-codex-mini` instead of `gpt-5.3-codex`: $124.14 became $61.22 over 2,140 messages. Neither price is attested for that id, so it is an estimate either way.

- **Antigravity Gemini 3.8 Flash route labels are one model, and nameless Antigravity CLI rows get a model.** [#541](https://github.com/Nanako0129/syrtis/pull/541) — thanks [@qqeet](https://github.com/qqeet) for [tokscale-core#34](https://github.com/Nanako0129/tokscale-core/pull/34)

  The labels `gemini-3.8-flash-control`, `-high`, `-low`, `-tiered` and `-n` now show as one `gemini-3.8-flash` row in the model report, with token totals unchanged. An Antigravity CLI row with no model name takes its model from the `model_enum` stored with it: M318 and M322 map to `gemini-3.8-flash`. Rows that were `unknown` at $0 and have a mapped value now show a model, a provider (`google` or `anthropic`) and a price. Only `-n` showed up in the maintainer's data, where 99 of its 101 rows carry M318; the other four labels and M322 were not seen locally. A usage attribution saved for a label, or for a row whose provider changed, no longer matches the new name; assign it again under Settings → Usage attribution.

- **OpenRouter's cache rates were dropped.** [tokscale-core#70](https://github.com/Nanako0129/tokscale-core/pull/70), pinned in [#529](https://github.com/Nanako0129/syrtis/pull/529) — thanks [@kizaki-R](https://github.com/kizaki-R)

  For a model with no matching author endpoint, the `input_cache_read` and `input_cache_write` rates published in OpenRouter's model list were dropped. They are kept now.

- **Settings cards turned dark grey with Reduce Transparency on.** [#524](https://github.com/Nanako0129/syrtis/pull/524) — thanks [@yellowsoar](https://github.com/yellowsoar)

  With Reduce Transparency on (Accessibility > Display), the cards drew a flat dark grey that was hard to read. The Settings window, the popover and their cards are now drawn in solid colors for light and dark appearance.

- **The Antigravity switch under Client tabs could not bring a hidden tab back.** [#536](https://github.com/Nanako0129/syrtis/pull/536) — thanks [@savourylie](https://github.com/savourylie)

  With a hidden-tab list saved from before the Antigravity IDE and CLI tabs were grouped, Settings → Dashboard → Client tabs (top bar) showed the Antigravity switch on while the tab stayed hidden, and turning it off and on again did not bring it back. The switch now clears the whole group, and the Agent limits and Individual items settings read the same list.

- **Adding a folder the app can't use no longer fails silently.** [#540](https://github.com/Nanako0129/syrtis/pull/540)

  A refused add now opens an alert with one sentence naming the reason, for the Claude, Pi and DeepSeek Harness lists, and "That folder can't be added." for Cursor profiles. A refused folder that is already stored stays in the list with a red mark whose hover text gives the sentence. Claude config dirs now also refuse `~/.claude` itself and every folder Syrtis already reads for your main Claude account, together with the folders that contain or sit inside them; before, adding `~/.claude` could zero the main account's usage in its quota windows. Other folders inside `~/.claude` are still accepted, and the list holds at most 8. A Cursor profile folder that is Cursor's own or repeats an earlier one is refused on its row while the other profiles keep syncing.

- **Antigravity capture asks first, reports failures, and no longer recreates a removed account.** [#540](https://github.com/Nanako0129/syrtis/pull/540)

  Turning on "Capture accounts agy signs into automatically" now opens "Turn on automatic capture?" with Cancel and Turn On, and nothing is written until you confirm. If it was already on, it stays on without asking. A failed automatic capture now shows the same sentence under the button as a failed manual one, unless agy is signed out. A capture whose Google reply doesn't name the same account is refused with "The login had an unexpected format. Nothing was saved." Remove now drops the account from the list before it deletes the Keychain copy, and a token refresh already in flight no longer writes the removed account back.

- **Accounts page copy says what Syrtis reads and sends.** [#540](https://github.com/Nanako0129/syrtis/pull/540)

  The Claude info popover says where the sign-in is read, that Syrtis doesn't log it, and which host receives which token. The sentence that said extra accounts "aren't shown separately" is gone, because each added folder gets its own Claude card. Each Remove button is named "Remove" followed by its folder path or account label.

  If sync leaves downloaded Cursor usage that is no longer needed and can't delete it, the Cursor section says "Some downloaded Cursor usage that is no longer needed couldn't be deleted. Syrtis will try again." If Cursor's settings are refused, it says "Cursor sync couldn't be set up, so nothing is being synced."

## Known issue

- **Capturing an Antigravity CLI (agy) login fails with agy 1.4.12.** [#540](https://github.com/Nanako0129/syrtis/pull/540)

  agy 1.4.12, the version checked, no longer stores in its saved login the account identity Syrtis reads from it. Both "Capture current agy login" and automatic capture stop with "agy's saved login doesn't say which Google account it is. Sign agy in again, then try again." Whether signing in again helps was not tested. v2.10.0 reads the same field, so this is not new; what changed is that a failed automatic capture now shows the sentence instead of nothing. A fix is planned for the next release.
