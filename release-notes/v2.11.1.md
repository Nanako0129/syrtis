## Fixes

- **Cursor usage sync can read a sign-in that Cursor stores encrypted, once you allow it.** [#549](https://github.com/Nanako0129/syrtis/pull/549) — thanks [@ohari5336](https://github.com/ohari5336), who reported the failure in [#520](https://github.com/Nanako0129/syrtis/issues/520) and confirmed the encrypted storage

  Cursor 3.27 and later can keep its sign-in encrypted (`cursor-safe-storage:v1:`). Syrtis could not read that form, so every Cursor profile failed to sync. A profile in that state now shows "Cursor stores its sign-in encrypted. Syrtis needs your permission to read it." and an "Allow Keychain access…" button in Settings → Accounts → Cursor. After you confirm there, macOS asks for permission to use the "Cursor Safe Storage" key from your Keychain. That key can decrypt everything Cursor stores encrypted. Syrtis uses it only to decrypt the Cursor sign-in of the profiles listed in Settings, keeps it in memory while Syrtis runs, and never saves or logs it. The sign-in is still sent only to cursor.com.

  macOS can ask on the first Cursor sync after Syrtis starts, after you press Allow, and on Sync Now when Syrtis holds no key. Later background syncs use the key in memory and never ask. If you press Deny, Syrtis withdraws your Allow and asks again only after you press "Allow Keychain access…" again. A sign-in stored in plaintext never asks.

  The encrypted path has not been tried on a real encrypted Cursor. Cursor 3.28.7 on the maintainer's Mac kept a plaintext sign-in, so the macOS dialog and the real Keychain read have not run anywhere; the decryption was tested with a generated fixture. Plaintext sync was checked on that Mac. If the encrypted read fails, the row shows a code such as `token_sealed_unreadable`.

  Grok Bot's fallback to Cursor's sign-in now treats an encrypted one as no Cursor login. Before, it sent the encrypted value to cursor.com as the login.

- **Antigravity CLI (agy) logins that store no account identity are captured again.** [#546](https://github.com/Nanako0129/syrtis/pull/546)

  This fixes the known issue in v2.11.0. agy 1.4.12, the version checked, stores no account identity in its saved login, so "Capture current agy login" and automatic capture stopped with "agy's saved login doesn't say which Google account it is." Syrtis now takes the account from Google's answer when it refreshes the login. An account you removed is not written back; for agy 1.4.x that is decided after the refresh, so one request to Google still happens. On the maintainer's Mac with agy 1.4.12, automatic capture listed the account with its email, and after removing it and signing agy out and in again it stayed off the list. Manual capture was covered by tests, not run on the device.

- **The popover no longer opens with the quota area empty after Syrtis has been idle.** [#552](https://github.com/Nanako0129/syrtis/pull/552)

  After a Cursor sync that downloaded new usage, the next popover showed the usage graph but "Checking agent limits…" on the Overview's first card and on the Agent quota cards until every provider had answered again. It now shows the last quota Syrtis already fetched, normally from the menu bar's own refresh, and updates it as before. If a Claude config folder or an Antigravity account changed since that quota was fetched, it is not shown. The maintainer's screen recordings, same steps before and after, showed the quota area empty on v2.11.0 and filled in the first frame with this fix.

- **A failed Cursor sync names its reason.** [#547](https://github.com/Nanako0129/syrtis/pull/547)

  The line under the Cursor switch and on each profile row now ends in the core's reason code, for example "Cursor usage couldn't be synced (http_status). Syrtis will try again later."

- **A quota card that fails to connect says why.** [#548](https://github.com/Nanako0129/syrtis/pull/548)

  The limits card and the time-window card show the category after the usual message, for example "Claude usage request failed (connectionRefused). Retrying automatically." Other categories include `timeout`, `dns`, `tls` and `connectionReset`; for rate limits and server errors the HTTP status (429 or 5xx) is shown. With a proxy that refused connections, the maintainer's Claude, Claude (.claude-work), Grok Build, Grok Bot and Codex limits cards showed `connectionRefused`; the time-window card was checked by a test.
