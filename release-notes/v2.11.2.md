## Fixes

- **Cursor usage syncs again for accounts moved to Cursor's new billing.** [#554](https://github.com/Nanako0129/syrtis/pull/554) — thanks [@ohari5336](https://github.com/ohari5336), who reported the failing profiles in [#520](https://github.com/Nanako0129/syrtis/issues/520) and confirmed they had been moved to the new billing

  For these accounts cursor.com answers the usage request Syrtis has always used with a success status but no list of usage events, so Syrtis stopped syncing them. Syrtis still asks the old endpoint first on every sync. Only when it answers that way does Syrtis read usage from Cursor's `v2/query-billing-items` endpoint instead. An account the old endpoint still serves is handled as before.

  Three things change for an account read this way:

  - Usage from before the switch stays. At the first successful read from the new endpoint, Syrtis freezes the rows it already had, in a separate file next to the usage file, and takes only the new endpoint's rows dated after a cutover time set at that moment. If a later sync is answered by the old endpoint again, that file is deleted.
  - Sessions are counted per day, because the new endpoint carries no conversation id, so one day's usage is one session.
  - A row Cursor reports with a charge of 0 (plan-included usage) carries no cost from Cursor, so Syrtis prices it from its own price table. A row with a positive USD charge keeps Cursor's amount. Only rows of the Cursor product are read.

  When a sync fails on this path, the line under the Cursor switch and on the profile row says so and ends in a code: "Cursor's new billing asks for a team for this account, which Syrtis can't read yet (billing_v2_team_required).", "Cursor's new billing didn't provide this account's usage (billing_v2_unavailable). Syrtis will try again later.", "Cursor's new billing has no usage for this account yet (billing_v2_no_items). Syrtis will try again later." or "Cursor returned usage of another account, so Syrtis saved nothing (billing_v2_principal_mismatch)." A failed sync leaves the usage already saved as it was.

  This has not run against an account that is actually on the new billing. The new endpoint's answers were tested against a local stand-in server, and its item layout comes from other tools' reports, not from an account of ours; the new endpoint asked the one account of ours that was checked for a team. The first thing likely to show on a real account is the "another account" line above. On the maintainer's Mac, an account still on the old billing synced to a usage file byte-identical to the previous build's, 28 events and 41549 tokens for 2026-11-04 UTC. The history rule, the per-day sessions and the pricing rule above were tested only and have not been seen on a device.

- **Antigravity cards show the Gemini bars again, and Gemini 4 Argon where the account has it.** [#553](https://github.com/Nanako0129/syrtis/pull/553)

  Antigravity cards had shown only the "Claude and GPT models" Weekly and Five Hour bars, while `agy /usage` listed Gemini Models, Claude and GPT models, and Gemini 4 Argon. Syrtis now asks Google's daily Code Assist host for the quota summary, which returns the Gemini groups; Gemini 4 Argon appears for an account Google has enabled it for and is labelled "Gemini 4 Argon · Weekly" in the pill row. If the summary request fails, Syrtis falls back to the per-model quota as before.

  To get that answer the four read-only quota requests to Google now send the User-Agent `antigravity/hub/2.23.0` followed by the platform and architecture (`darwin/arm64` or `darwin/amd64`), the way the Antigravity hub does; the token refresh does not. On the maintainer's Mac, with a test build, both accounts showed Gemini Weekly and Five Hour again, and the account with Argon showed Gemini 4 Argon Weekly at 88% left, against 0.879 in `agy /usage`. The other account has no Argon group, which matches Google enabling it per account.

- **A merged Antigravity card says when the account's own quota check failed.** [#555](https://github.com/Nanako0129/syrtis/pull/555)

  When agy is signed in to an account that is also a captured Antigravity account, the two cards are merged. If the captured account's own fetch had failed (for example, Google blocked it), the merged card's windows read "Pace unavailable · account identity unavailable", which did not say why. They now read "Pace unavailable · this account's quota check failed". The card's usage, reset time and label are unchanged. The bundled self-test covers it, and each new check was shown to fail when the code it guards is broken; it has not been seen on a running app.

## Known issues

- **The failed check's cause is not shown on the merged card.** The same pace line appears whatever made the captured account's fetch fail (blocked, expired login).
- **An extra Antigravity card appeared once.** On the first launch of the test build of #553, the Antigravity primary showed an extra card from the agy CLI that did not come back on relaunch. The cause is not known.
